\section{Software Requirements Specification}
\label{ch:srs}

\subsection{Purpose and Scope of the SRS}
This chapter condenses the IEEE 830 SRS of Phase~II (\texttt{docs/SRS\_EcoMesh\_Group20.pdf}): \emph{what} EcoMesh must do, not how. The scope is one deployment of cooperating nodes with ten features (discovery, message composition, forwarding, routing, priority, reliability, store-and-forward, security, logging, rescue dashboard) and no server in any mode.
\subsection{Intended Users and Stakeholders}
The \emph{trapped user} originates an SOS and needs one prominent control and no configuration; the \emph{relay user} carries others' traffic and must not be able to read it; the \emph{gateway operator} holds the outside link; the \emph{rescue coordinator} monitors the SOS queue, topology and statistics; the \emph{administrator} assigns node identifiers and who hears whom.

\subsection{Overall Product Description}
Every node runs the same program: HELLO beacons build a neighbour table, link-state reports a graph; Dijkstra selects next hops; a per-hop priority queue orders transmissions; ACK, retry, dedup and store-and-forward give reliability; AES-256-GCM and Ed25519 give confidentiality and authenticity; an embedded web server exposes the node to a browser. A configured peer list replaces multicast where needed (DIS-7).

\subsection{Non-Functional Requirements}
\label{sec:nfr}
\textbf{Performance:} at least 90\,\% delivery on 40 nodes at 20\,\% loss; convergence within 15\,s; delivery resumed within 10\,s of a node failure; an SOS measurably faster under load. \textbf{Scalability:} at least 50 nodes without reconfiguration. \textbf{Availability and reliability:} no single point of failure; no message discarded while retention capacity remains. \textbf{Security and privacy:} payloads unreadable by relays; tampering and forged SOS rejected; every field validated; private keys never transmitted. \textbf{Usability:} one prominent SOS control needing a sustained press; status visible within 2\,s. \textbf{Maintainability and portability:} one module per concern; the engine is independent of the link technology. \textbf{Resources:} one process on one event-loop thread with bounded queues (Chapter~\ref{ch:perf}).

\subsection{Hardware and Software Requirements}
\textbf{Hardware:} laptops (Windows~11) on a Wi-Fi network or a phone hotspot; no server. \textbf{Software:} Python~3.10 with \texttt{asyncio}, \texttt{cryptography} (AES-256-GCM, Ed25519) and SQLite in WAL mode; FastAPI, uvicorn and \texttt{websockets}; React~18 with Vite, Tailwind and d3-force, installable as a PWA; pytest and pytest-asyncio; Git and GitHub.

\subsection{Constraints and Assumptions}
\textbf{Constraints:} one semester (17~August to 2~November 2026); three members; no radio hardware, so a neighbour-restricted LAN emulates the radio; about 50 nodes; no machine learning or native app. \textbf{Assumptions:} the software is installed before an incident; every device can reach another, directly or through others; batteries last the incident; a gateway or rescue node exists for messages to leave; node identifiers are unique.
\subsection{Use Cases and User Stories}
\textbf{UC1:} a trapped user holds the SOS control; the highest-priority message is sent and its status shown. \textbf{UC2:} with no route the message is retained and flushed when a path appears. \textbf{UC3:} a relay user forwards automatically without reading the payload. \textbf{UC4:} a gateway node advertises its role. \textbf{UC5:} a rescue coordinator sees the SOS queue with routes, and the topology. \textbf{UC6:} an administrator sets who hears whom in a topology file.
