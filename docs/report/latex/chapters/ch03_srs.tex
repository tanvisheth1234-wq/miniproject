\section{Software Requirements Specification}
\label{ch:srs}

\subsection{Purpose and Scope of the SRS}
This chapter condenses the IEEE 830 SRS of Phase~II and its final revision, SRS version~2 (\texttt{docs/}), which adds the final device screens: \emph{what} EcoMesh must do, not how. Its scope is one deployment of cooperating nodes with ten features (discovery, composition, forwarding, routing, priority, reliability, store-and-forward, security, logging, rescue dashboard) and no server.
\subsection{Intended Users and Stakeholders}
The \emph{trapped user} raises an SOS and needs one clear control and no set-up; the \emph{relay user} carries other people's traffic and must not be able to read it; the \emph{gateway operator} holds the outside link; the \emph{rescue coordinator} watches the SOS queue, the topology and the statistics; the \emph{administrator} assigns node identifiers and decides which nodes can hear each other.

\subsection{Overall Product Description}
Every node runs the same program: HELLO beacons fill a neighbour table, link-state reports build a graph, Dijkstra picks next hops, a per-hop priority queue orders sending, ACK, retry, dedup and store-and-forward give reliability, AES-256-GCM and Ed25519 give confidentiality and authenticity, and a built-in web server shows the node in a browser. A configured peer list replaces multicast where needed (DIS-7).

\subsection{Non-Functional Requirements}
\label{sec:nfr}
\textbf{Performance:} at least 90\,\% delivery on 40 nodes at 20\,\% loss; convergence within 15\,s; delivery resumed within 10\,s of a node failure; an SOS measurably faster under load. \textbf{Scalability:} at least 50 nodes with no change of configuration. \textbf{Availability and reliability:} no single point of failure; no message discarded while there is room to keep it. \textbf{Security and privacy:} relays cannot read payloads; tampering and forged SOS are rejected; every field is validated; private keys never leave the device. \textbf{Usability:} one prominent SOS control that needs a sustained press; status on screen within 2\,s; typing optional where the browser supports voice input. \textbf{Maintainability and portability:} one module per concern, and an engine independent of the link technology. \textbf{Resources:} one process on one event-loop thread with bounded queues (Chapter~\ref{ch:perf}).

\subsection{Hardware and Software Requirements}
\textbf{Hardware:} laptops running Windows~11 on a Wi-Fi network or a phone hotspot; optionally a phone that opens a device's screen; no server. \textbf{Software:} Python~3.10 with \texttt{asyncio}, the \texttt{cryptography} library and SQLite in WAL mode; FastAPI, uvicorn and \texttt{websockets}; React~18 with Vite, Tailwind and d3-force; a Chromium-based browser for voice input; pytest and pytest-asyncio; Git and GitHub.

\subsection{Constraints and Assumptions}
\textbf{Constraints:} one semester (17~August to 2~November 2026); three members; no radio hardware, so a LAN restricted to configured neighbours emulates the radio; about 50 nodes; no machine learning or native app. \textbf{Assumptions:} the software is installed before an incident; every device can reach another directly or through others; batteries last the incident; a gateway or rescue node exists for messages to leave by; node identifiers are unique.
\subsection{Use Cases and User Stories}
\textbf{UC1:} a trapped user picks a request type, gives a location by typing or speaking, and holds the SOS control; the message is sent at the highest priority and its progress is shown. \textbf{UC2:} with no route the message is held and sent when a path appears. \textbf{UC3:} a relay user forwards traffic automatically without reading it. \textbf{UC4:} a gateway node announces its role. \textbf{UC5:} a rescue coordinator sees the requests with their routes, replies and filters them. \textbf{UC6:} an administrator sets which nodes can hear each other in a topology file.
