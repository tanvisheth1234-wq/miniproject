Every number in this chapter is generated by scripts in \texttt{docs/report/evidence/} from stored measurements; none is typed by hand. Two kinds of measurement are never mixed: the \emph{simulator} (real \texttt{Node} objects over an in-memory transport with seeded loss and latency on a virtual clock, so the specified 3\,s/10\,s/4\,s timers run in a fraction of a second) and \emph{live devices} (real processes, real TCP, real timers).

\subsection{Scalability Requirements}
The SRS requires operation at up to fifty nodes, at least 90\,\% delivery on a forty-node network with 20\,\% loss, convergence within 15\,s and recovery within 10\,s (Section~\ref{sec:kpi}). The live deployment is five devices; larger sizes exist only in the simulator and are labelled as such.

\subsection{Workload and Load Model}
Each scenario fixes a topology, a per-link loss rate, 5--40\,ms link latency, 10--90 messages (a fraction of them SOS) spread over a window, a settling period and a failure script. Each runs on many seeds; a seed fixes loss and traffic, so runs reproduce and routing modes can be compared on identical seeds. The loss sweep varies per-link loss from 0 to 50\,\% on a 21-node mesh; the scale sweep varies the mesh from 10 to 65 nodes at 5\,\% and 20\,\% loss; the throughput test sends 100 to 2\,000 simultaneous messages over a three-node line. The live run sent 30 sequential SOS, caused 8 relay failures and 4 gateway outages with 5 held messages each.

\subsection{Resource Utilization}
\textbf{Simulator:} CPU time and Python heap peak of the whole simulated mesh in one process (Table~\ref{tab:scale}); the 65-node mesh used about 13\,MB of heap. \textbf{Live devices:} working set and CPU of each real process, engine plus web server (Table~\ref{tab:live}): about 53\,MB and 0.4--1.9\,\% of one core when idle. \textbf{Storage:} the SQLite file grows with logged events (one row per event) and is the only unbounded structure; retention is bounded at 500 messages. \textbf{Network:} data transmissions per delivered message are in Tables~\ref{tab:loss} and~\ref{tab:scale}; HELLO and link-state control traffic is not logged per packet and is not included.

\subsection{Concurrent Processing}
A node is single-threaded and cooperative with no locks. On a three-node line with ACKs requested, \ThrMidRate\ messages per second were delivered at 1\,000 simultaneous sends and \ThrMaxRate\ per second at \ThrMaxN\ (all ACKed within \ThrMaxAck\,s), with a SQLite commit per event. The concurrency tests (Chapter~\ref{ch:test}) confirm exactly-once delivery of 200 simultaneous sends.

\subsection{Scheduling and Synchronization Analysis}
The scheduling policy is priority scheduling with ties broken oldest-first, re-applied at every hop. The scheduling metric is the latency advantage of an SOS over routine traffic on the same trip, measured in a deliberately congested scenario (a radio that sends one packet per 80\,ms) because on an idle network there is nothing to overtake. No synchronisation primitive exists because shared state is touched only on the event-loop thread. Results are in Section~\ref{sec:perfresults}.

\subsection{Performance Measurement}
\textbf{Experimental setup and test environment:} one Windows~11 laptop, Python~3.10; simulator runs used a process pool; live runs used five processes on the loopback interface with HELLO 1\,s, neighbour timeout 4\,s, link-state 2\,s, ACK timeout 3\,s and 3 retries. \textbf{Workload:} as in Section~8.2. \textbf{Tools and method:} per-process memory and CPU from operating-system counters; latency by polling each device's own API every 20\,ms (so it carries up to 20\,ms of error); simulator metrics are queries over the nodes' SQLite logs; repeated seeded runs and trials as stated beside each result.

\textbf{Weighted versus hop-count routing (Figure~\ref{fig:results}b).} In the designed topology the 2-hop shortcut crosses a link with 45\,\% loss and the 3-hop path is clean; messages are best-effort, so a poor route shows up directly as loss. Weighted routing delivered \HopW\,\% and hop-count routing \HopH\,\%, and weighted won on \HopWins\ of \HopRuns\ identical seeds. It is a \emph{designed} topology that exposes hop count's weakness, so it shows that the cost function avoids a lossy shortcut, not that the same gap occurs on every mesh.

\textbf{Scalability.}
\input{generated/scale_all.tex}
At 5\,\% loss delivery is 100\,\% to 50 nodes and 98.9\,\% at 65; at 20\,\% loss it holds above 95\,\% to about 43 nodes and falls to 88.2\,\% at 50 and 86.0\,\% at 65. Transmissions per delivered message grow roughly linearly with size (paths lengthen), not quadratically as flooding would.

\textbf{Recovery and convergence.} Both are quantised by design constants (Figure~\ref{fig:results}d). Convergence comes in multiples of the 5\,s gossip interval (5.2, 10.2 or 15.2\,s). Recovery splits in two: 23 of 50 trials recovered in under 10\,s because ACK failures penalise the failing link at once; the other 27 recovered at 10.2--10.25\,s, the 10\,s heartbeat timeout plus the 0.25\,s measurement step, because the sender did not learn of the death until its neighbour timed out.

\subsection{Bottleneck Identification}
Failure-detection latency (recovery is bounded by the 10\,s heartbeat timeout); the 4\,s ACK timeout under loss; the 5\,s convergence granularity of the link-state interval; one SQLite commit per event; and wholesale route-cache invalidation.

\subsection{Optimization and Improvement}
No optimisation was applied after these measurements, so there is no before-and-after comparison to report. The data point to the changes with the best return: a neighbour timeout near 6--7\,s so that recovery fits inside 10\,s, an immediate link-state report on topology change, an adaptive ACK timeout from the measured round-trip time, and per-destination cache invalidation. Each is a one-constant or one-function change that can be re-measured with the same scripts.

\subsection{Cloud Deployment and Resource Utilization}
Not applicable: the system has no server and was not deployed on cloud infrastructure.

\subsection{Scalability Limitations}
The largest tested sizes are 65 simulated nodes and 5 live devices. \emph{Measured:} 98.9\,\% delivery at 65 nodes with 5\,\% loss and 86.0\,\% with 20\,\% loss. \emph{Not tested:} more than 65 nodes, wireless interference and mobility; capacity beyond the tested sizes is a projection, not a result. The live timings share one machine and exclude wireless delay.
