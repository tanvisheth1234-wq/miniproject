Every number in this chapter is generated by scripts in \texttt{docs/report/evidence/} from stored measurements; none is typed by hand. Two kinds of measurement are never mixed: the \emph{simulator} (real \texttt{Node} objects over an in-memory transport with seeded loss and latency on a virtual clock, so the specified 3\,s/10\,s/4\,s timers run in a fraction of a second) and \emph{live devices} (real processes, real TCP, real timers).

\subsection{Scalability Requirements}
The SRS requires up to fifty nodes, at least 90\,\% delivery on forty nodes at 20\,\% loss, convergence within 15\,s and recovery within 10\,s (Section~\ref{sec:kpi}); sizes above the five live devices exist only in the simulator.
\subsection{Workload and Load Model}
Each scenario fixes a topology, a per-link loss rate, 5--40\,ms link latency, 10--90 messages (some SOS), a settling period and a failure script, and runs on many seeds, so routing modes are compared on identical traffic. Sweeps vary loss from 0 to 50\,\% (21 nodes) and size from 10 to 65 nodes (5\,\% and 20\,\% loss); throughput uses 100--2\,000 simultaneous sends on a three-node line; the live run sent 30 SOS with 8 relay failures and 4 gateway outages.

\subsection{Resource Utilization}
\textbf{Simulator:} CPU time and Python heap of the whole simulated mesh (Table~\ref{tab:scale}); 65 nodes used about 13\,MB. \textbf{Live devices:} about 53\,MB and 0.4--1.9\,\% of one core per idle process (Table~\ref{tab:live}). \textbf{Storage:} the SQLite log grows one row per event; retention is bounded at 500 messages. \textbf{Network:} transmissions per delivered message are in Table~\ref{tab:scale}.
\subsection{Concurrent Processing}
A node is single-threaded and cooperative with no locks. On a three-node line with ACKs, \ThrMidRate\ messages per second were delivered at 1\,000 simultaneous sends and \ThrMaxRate\ per second at \ThrMaxN\ (all ACKed within \ThrMaxAck\,s); the concurrency tests (Chapter~\ref{ch:test}) confirm exactly-once delivery.

\subsection{Scheduling and Synchronization Analysis}
Scheduling is by priority, oldest first on ties, re-applied at every hop; its metric is the SOS latency advantage in a deliberately congested scenario (Section~\ref{sec:perfresults}), since on an idle network there is nothing to overtake. No synchronisation primitive is needed because shared state is touched only on the event-loop thread.

\subsection{Performance Measurement}
One Windows~11 laptop with Python~3.10; live runs used five processes on loopback (HELLO 1\,s, neighbour timeout 4\,s, link-state 2\,s, ACK timeout 3\,s, 3 retries). Memory and CPU come from operating-system counters, live latency from polling each device's API every 20\,ms (up to 20\,ms error), and simulator metrics from queries over the nodes' SQLite logs.
\subsection{Performance Results}
\label{sec:perfresults}
\textbf{Reliability under loss} (Figure~\ref{fig:results}a, 21-node grid, 8 seeded runs per point). Delivery stays at or above 98\,\% to 20\,\% loss and falls to 61\,\% at 50\,\%; each lost ACK costs a 4\,s timeout, so median latency goes from tens of milliseconds at 0\,\% to seconds at 20--30\,\%.

\textbf{Weighted versus hop-count routing (Figure~\ref{fig:results}b).} In the designed topology the 2-hop shortcut crosses a link with 45\,\% loss and the 3-hop path is clean; messages are best-effort, so a poor route shows up directly as loss. Weighted routing delivered \HopW\,\% and hop-count routing \HopH\,\%, and weighted won on \HopWins\ of \HopRuns\ identical seeds. It is a \emph{designed} topology that exposes hop count's weakness, so it shows that the cost function avoids a lossy shortcut, not that the same gap occurs on every mesh.

\textbf{Priority under load.} The congested scenario (16 nodes, 90 messages to the same destination, 15\,\% SOS) gives an SOS a median latency \SosAdv$\times$ lower than routine traffic. Only here do SOS and routine messages take the same trip, so only here is the comparison fair.

\textbf{Scalability.}

At 5\,\% loss delivery is 100\,\% to 50 nodes and 98.9\,\% at 65; at 20\,\% loss it holds above 95\,\% to about 43 nodes and falls to 88.2\,\% at 50 and 86.0\,\% at 65. Transmissions per delivered message grow roughly linearly with size, not quadratically as flooding would.

\textbf{Recovery and convergence} are quantised by design constants (Figure~\ref{fig:results}d): convergence comes in multiples of the 5\,s gossip interval, and recovery takes under 10\,s in 23 of 50 trials (ACK failures penalise the link at once) and 10.2--10.25\,s in the other 27, bounded by the 10\,s heartbeat timeout.

\subsection{Bottleneck Identification}
Failure detection (recovery is bounded by the 10\,s heartbeat timeout), the 4\,s ACK timeout under loss, the 5\,s link-state interval, one SQLite commit per event and wholesale route-cache invalidation.
\subsection{Optimization and Improvement}
No optimisation was applied after these measurements, so there is no before-and-after comparison. The data point to a neighbour timeout near 6--7\,s (recovery inside 10\,s), an immediate link-state report on topology change, an adaptive ACK timeout and per-destination cache invalidation.
\subsection{Cloud Deployment and Resource Utilization}
Not applicable: the system has no server and was not deployed on cloud infrastructure.

\subsection{Scalability Limitations}
Tested up to 65 simulated nodes (98.9\,\% delivery at 5\,\% loss, 86.0\,\% at 20\,\%) and 5 live devices. More nodes, wireless interference and mobility were not tested; capacity beyond these sizes is a projection.
