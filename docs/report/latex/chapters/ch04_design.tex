\section{System Architecture and Design}
\label{ch:design}

\subsection{Overall System Architecture}
A node is one operating-system process. Inside it \texttt{asyncio} runs discovery (HELLO every 3\,s, timeout 10\,s), link-state gossip (every 5\,s), the receive path, the sender (priority queue), the store-and-forward flush (every 10\,s) and the API server on one event-loop thread. Every activity reaches the network only through the \texttt{Transport} interface (Figure~\ref{fig:arch}). Shared mutable state is the neighbour table, the mesh graph and the pending-ACK map (plus the dedup set and the retention queue, each owned by one component); on one thread there are no locks and no data races by construction.

\textbf{Wire protocol.} A fixed big-endian header (Table~\ref{tab:header}) is followed by the traversed path, the payload and an optional 64-byte signature. The path is carried on the wire for loop detection and so that the interface can show ``relayed via $n$ nodes''. HELLO is a one-hop shout, LINK\_STATE is unicast to neighbours, and DATA and ACK use TCP per hop, so each hop is ordered and reliable though the end-to-end path is not.

\subsection{Architecture Selection and Justification}
\textbf{Layered and transport-agnostic.} One boundary separates ``how bytes move'' from everything else. It gives a deterministic simulator, socket-free unit tests and an honest answer to the radio objection (a BLE transport is a fourth implementation, not a rewrite). \textbf{Single-threaded \texttt{asyncio} rather than threads.} Four activities share three structures; on one loop there are no locks or races, so correctness does not rest on lock discipline. \textbf{Peer-to-peer rather than client--server.} A server is a single point of failure and the very infrastructure being argued against. \textbf{Link state rather than flooding or on-demand discovery.} Flooding collapses under load and on-demand discovery delays the first emergency packet. \textbf{Per-node SQLite (WAL).} File-based, no server, and the API can read while the engine writes.

\subsection{Database Design}
\label{sec:db}
Each node keeps its own SQLite database (WAL mode, plain \texttt{sqlite3} and raw SQL: three tables, so an ORM would add indirection for nothing). Every metric is a query over it (SRS 6.1).
\begin{figure}[!htbp]
\centering
\includegraphics[width=0.7\textwidth]{figures/fig_er.pdf}
\caption{Entity--relationship diagram of the per-node database (PK primary key, IDX secondary index, FK logical foreign key)}
\label{fig:er}
\end{figure}
\textbf{Relational schema.} \texttt{messages}(\texttt{msg\_id} PK, \texttt{src}, \texttt{dst}, \texttt{priority}, \texttt{direction} in sent/received/forwarded, \texttt{status} in pending/delivered/failed/queued\_sf, \texttt{body}, \texttt{created\_ms}, \texttt{resolved\_ms}, \texttt{hop\_count}, \texttt{path}); \texttt{events}(\texttt{id} PK, \texttt{ts\_ms}, \texttt{kind}, \texttt{msg\_id}, \texttt{peer}, \texttt{detail}); \texttt{peers}(\texttt{node\_id} PK, \texttt{role}, \texttt{last\_seen\_ms}, \texttt{link\_quality}, \texttt{public\_key}). \textbf{Keys and integrity constraints.} \texttt{msg\_id} is a UUID and is the join key between a node's messages and events; \texttt{messages.body} holds plaintext only if the node is the source or destination; writes to \texttt{messages} are upserts, so a message moves pending $\rightarrow$ queued\_sf $\rightarrow$ delivered without duplicate rows; \texttt{events.msg\_id} and \texttt{events.peer} are logical, not declared, foreign keys because a relay logs events for messages it never stores and for peers that may have expired. \textbf{Normalisation.} Third normal form except \texttt{messages.path}, a comma-separated list kept denormalised because it is always read and written whole. \textbf{Indexing.} \texttt{idx\_events\_ts} serves ``events since $t$'' for the live feed; \texttt{idx\_msg\_status} serves the retained-message counter. \textbf{Sample records} from a real run are in Table~\ref{tab:samples}; the relay's row carries no body.

\subsection{Security and Error Handling Design}
\label{sec:secdesign}
\textbf{Authentication.} Nodes have no user accounts; a node's identity is its Ed25519 key pair, distributed in HELLO and link-state reports, and every signed packet is verified against the sender's known key. An unknown signer is rejected. \textbf{Authorization.} Authority follows the node role: only GATEWAY and RESCUE nodes are valid terminals for \texttt{RESCUE\_\_}; any node may relay. The relay path never decrypts or stores content it does not own, and a relay that does not hold the session key sees only ciphertext; because one pre-shared key serves the whole mesh, a node that \emph{does} hold it could read what it forwards, which per-pair key agreement would remove (Section~\ref{sec:limits}). \textbf{Input validation.} Every packet field is range-checked before use; a violation raises \texttt{PacketError} and the packet is dropped, never forwarded. \textbf{Exception handling.} A bad packet is dropped and logged and never raised into the event loop; crypto failures collapse into one exception type and \texttt{verify} returns \texttt{False} instead of raising. \textbf{Logging.} Each drop has a named event kind (\texttt{drop\_ttl}, \texttt{drop\_dup}, \texttt{drop\_loop}, \texttt{drop\_signature\_invalid}, \texttt{drop\_decrypt\_failed}, \ldots) in the node's database. \textbf{Protection of sensitive data.} Payloads are AES-256-GCM ciphertext with a random 12-byte nonce; plaintext is stored only on the originator and destination; private keys stay in local memory and are never transmitted. The signature covers the identity fields (version, type, priority, flags, src, dst, msg\_id, timestamp, payload) and not the whole header, because TTL, hop count and path change at every relay and a signature over them could never verify beyond the first hop; the retransmission counter is excluded so a retry keeps its identity.
