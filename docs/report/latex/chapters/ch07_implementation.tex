\section{Implementation and Module-Wise Coding}
\label{ch:impl}

\subsection{Development Environment}
The system is written in Python~3.10 with \texttt{asyncio}, the \texttt{cryptography} library and SQLite; the API uses FastAPI, uvicorn and pydantic; the web application uses React~18, Vite and Tailwind; testing uses pytest and pytest-asyncio; version control is Git on GitHub. The source is about 6\,500 lines of Python (\texttt{mesh/}, \texttt{api/}, \texttt{sim/}, \texttt{story/}), 4\,500 lines of tests and 3\,100 lines of React.

\subsection{Overall Implementation Strategy}
The build order followed what blocks what. \textbf{Phase~1:} the 52-byte packet and the \texttt{Transport} interface, so every track could work against a stable boundary. \textbf{Phase~2:} discovery, single-hop relay and the simulated transport, so that routing and reliability could be tested in one process. \textbf{Phase~3:} routing, reliability, security and storage, wired into \texttt{Node}. \textbf{Phase~4:} the API and React application, the scenario runner and metrics, engine fixes found by integration, and the multi-device deployment.

\subsection{Front-End Implementation}
There is one app, the \textbf{device screen} (\texttt{story/node.html}): a single page that every device serves and that acts as a \emph{survivor phone}, a \emph{gateway} view or a \emph{rescue console} depending on the device's role. A phone is only a screen; the engine runs on a laptop and the phone opens the page over the same Wi-Fi or hotspot. The survivor screen is designed to be read under stress. It has a plain status line; nine request types in a grid (Medical emergency, selected by default, Injured, Trapped, Fire or smoke, Unsafe building, Need water, Need food, Need medicine, and Elderly or child needs help); a location box; an SOS button that must be held for about 1.2\,s so that it is not sent by accident; an ``I am safe'' check-in that never delays an SOS; a form for a text message to a named device; the rescue team's reply above a step-by-step progress tracker; and the nearby phones with their signal strength. \textbf{Voice input.} A \emph{Speak} button beside the location box and the message box uses the browser's speech recognition to turn speech into text, which helps a person who is injured or cannot type. The recognition service in Chrome needs an internet connection and a page opened on \texttt{localhost} or \texttt{https}, so where it is missing the button is disabled with the reason, a failure such as a blocked microphone is explained in one line, and typing always works. The rescue console lists each request with its type, location, route and age, keeps check-ins in a separate Marked safe list, filters by kind and by request type, offers replies with quick phrases, a message history filtered by priority and direction, CSV export, counters, and a network map that shows link quality and highlights the route of each new message. Every screen also has a live panel, ``What this device is doing'', that turns the device's event log into plain English. Screens are shown in Section~\ref{sec:shots}. The \textbf{simulation lab} (\texttt{ui/}, a React PWA served by \texttt{api/server.py}) is not part of the demonstration; it remains because it produced the experiments of Chapter~\ref{ch:perf}.

\subsection{Back-End Implementation}
The back end is FastAPI with a WebSocket. The engine server (\texttt{api/server.py}) serves the simulation lab: snapshots, kill and revive, link edits, routes (weighted and hop-count), statistics, a message's full story, a protocol inspector, a security drill, scenario jobs, and \texttt{/ws}, which streams every logged event. Each device server (\texttt{story/node.py}) exposes \texttt{/api/me} (everything its screen needs), \texttt{/api/sos} (the need and location travel as structured fields), \texttt{/api/send} (a text message to a named device), \texttt{/api/safe} (an ``I am safe'' check-in at the lowest priority), \texttt{/api/events} (the event log in plain English), \texttt{/api/history} (messages filtered by priority and direction), \texttt{/api/export.csv} (the received requests, rescue device only) and \texttt{/api/power}; started with \texttt{-{}-phone} it serves its screen on every network interface so a phone on the same Wi-Fi can open it. Request bodies are validated with pydantic, and engine errors map to clear HTTP errors.

\subsection{Database Implementation}
The three tables of Section~\ref{sec:db} are created with \texttt{CREATE TABLE IF NOT EXISTS}, WAL mode is set at connection time, and the two indexes are created with the schema. Queries used include retained messages by status (\texttt{SELECT * FROM messages WHERE status = ?}), a message's timeline (\texttt{SELECT * FROM events WHERE msg\_id = ? ORDER BY ts\_ms}), event counters (\texttt{SELECT COUNT(*) FROM events WHERE kind = ?}), and the upsert \texttt{INSERT \ldots ON CONFLICT(msg\_id) DO UPDATE}. Every write commits immediately.

\subsection{Communication and Concurrency Implementation}
\label{sec:lan}
The original \texttt{UdpTcpTransport} could not carry a complete \texttt{Node}: it never learned a HELLO sender's address, and it reported the packet's \emph{original} source instead of the previous hop, which breaks link-state flooding. \texttt{lan\_transport.py} fixes both. A JSON \textbf{topology file} lists every device (role, host, port) and the links (who can hear whom); a device talks only to its configured neighbours, which emulates limited radio range as stated in the scope and satisfies DIS-7, so no multicast is needed. Each connection starts with the previous hop's identity followed by the unmodified packet. A \textbf{power switch} makes a device neither send nor hear, like a dead radio. \texttt{python -m story.node -{}-id L1} starts one device (engine plus a small web server); five of them, started together on one machine or one per laptop, form the mesh, each with its own SQLite log, port and screen. In the two-laptop demonstration L1--L3 ran on one laptop and L4--L5 on the other, joined through a phone hotspot (Figure~\ref{fig:deploy}). Recovery is layered: TCP per hop; ACK, retry and re-route end to end; store-and-forward when retries run out.

\subsection{Integration of Modules}
\texttt{Node} registers one dispatcher on the transport that feeds each packet to discovery (HELLO), gossip (LINK\_STATE) and relay (DATA, ACK); each ignores types it does not own. Callbacks join the pieces: peer-up adds a graph edge and logs it, a topology change invalidates cached routes, relay hooks write the log, and the ACK loop reports failures to gossip at once. The screens read the same objects and database as the engine.

\subsection{Implementation Challenges and Resolutions}
The main difficulties (Table~\ref{tab:defects}) were a receive callback heard by only one layer, dead nodes that stayed routable, signatures that failed after the first relay (fixed by signing identity fields only), ACKs lost at relays, a hostile packet raising \texttt{UnicodeDecodeError}, a Windows hang in \texttt{Node.stop()}, and a transport unable to run a full node (fixed by \texttt{LanTransport}).
