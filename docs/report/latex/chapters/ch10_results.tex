\subsection{Functional Results}
Of the 68 requirements \NAuto\ are verified by automated tests, \NAutoUI\ with a screen check, \NInspect\ by inspection and \NManual\ manually; none is partial. The key stories (multi-hop SOS, re-routing around a failed relay, hold and later delivery) ran on real devices, and the browser run repeats them with the nine request types and voice input (\NDevPass\ of \NDevChecks\ pass).
\subsection{Performance Results}
Table~\ref{tab:kpival}: \CollDel\,\% delivery on 40 nodes at 20\,\% loss with failures, SOS \SosAdv$\times$ faster under load, live SOS in a median 32\,ms, failover in about 4.1\,s, held messages flushed in about 4.2\,s.
\subsection{Comparison with Existing Systems}
Other systems were not run, so the comparison rests on documented properties (Table~\ref{tab:compare1}) and one fair baseline, hop count on identical seeds (\HopW\,\% against \HopH\,\%); no delivery claim is made for systems that publish no measurements.

\subsection{Discussion of Findings}
Hop count is a poor proxy for delivery: a weak shortcut loses almost half the traffic under hop count and almost none under the weighted cost. Timer constants, not algorithms, set recovery and convergence, which shows what to tune. Priority matters once links queue, which is the disaster condition.

\subsection{Practical Applicability}
A deployment needs devices running the node, a topology file (or multicast), a gateway or rescue device and a shared network; it works today as a building safety system on laptops, and a radio transport would make it phone-to-phone.
