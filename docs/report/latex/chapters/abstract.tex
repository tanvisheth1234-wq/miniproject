\section*{Abstract}
\addcontentsline{toc}{section}{Abstract}

\textbf{Problem.} When an earthquake, fire or building collapse destroys communication infrastructure, every mainstream messaging application fails with it, even when the devices of the trapped people can still reach each other. Connectivity after a disaster survives only in scattered pockets and normally helps only the person who holds it.

\textbf{Motivation and objectives.} Rescue is time-critical, so the aim is a system that makes one person's connectivity serve everyone and lets an SOS overtake routine traffic at every hop: self-organising, link-quality-weighted routing, reliable delivery with a delay-tolerant fallback, authenticated and encrypted messages, and measured performance.

\textbf{Proposed solution.} EcoMesh makes every participating device an endpoint and a relay. A message hops from device to device until it reaches a gateway with an outside link, a rescue device, or a store-and-forward queue that holds it until a path appears. No internet, tower or server is needed.

\textbf{Technologies and engineering concepts.} Python with \texttt{asyncio} (one event-loop thread per node, no locks); a custom 52-byte binary protocol; link-state gossip; Dijkstra routing over the cost $1+5(1-q)+3f$; a per-hop priority queue; ACK with retry and route recomputation; AES-256-GCM and Ed25519; per-node SQLite logs; FastAPI and WebSocket; a React web application; and a transport interface so one engine runs on an in-memory simulator, on loopback sockets and on separate laptops.

\textbf{Key implementation features.} Neighbour discovery with measured link quality; network-wide link-state flooding with sequence numbers; duplicate suppression; bounded store-and-forward that never evicts an SOS for routine traffic; signatures that survive multi-hop relaying; a survivor screen with a hold-to-send SOS button and a rescue console.

\textbf{Testing methodology.} \NTests\ automated tests (unit, integration, boundary, fuzz, replay, concurrency and a three-node mesh over real TCP), a requirement-to-test table for 68 requirements, seven simulator scenarios with seeded repeated runs, loss and scale sweeps up to 65 nodes, and measurements on five real processes over real sockets.

\textbf{Results.} On a 40-node mesh with 20\,\% per-link loss and injected failures, \CollDel\,\% of messages were delivered (50 runs). Weighted routing delivered \HopW\,\% against \HopH\,\% for hop-count routing on identical seeds. Under load an SOS had a \SosAdv$\times$ lower median latency than routine traffic. On five live processes an SOS arrived in a median of 47\,ms, the sender re-routed around a failed relay in a median of 4.0\,s, and every held message was delivered after a gateway outage. Convergence and recovery met their targets on average but not in every run, and delivery fell below 90\,\% above about 43 nodes at 20\,\% loss.

\textbf{Practical applicability and limitations.} The system is directly usable as an institutional safety network on laptops. The radio link is emulated by a neighbour-restricted LAN, so it does not yet run phone to phone; a Bluetooth or Wi-Fi Direct transport, adaptive timers, a timed usability study and per-pair key agreement are the main future work.
